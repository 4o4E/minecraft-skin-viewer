# 渲染文件缓存设计

## 目标

HTTP 渲染接口迁移到 Tavolo 后，静态图和 GIF 都在服务端 CPU 侧完成。缓存目标是复用相同皮肤、相同渲染参数的最终图片结果，减少重复的 3D voxel overlay 建模、逐帧光栅化、GIF 编码和量化开销。

## 缓存范围

缓存 `/render/{type}/{content}/{position}` 的最终响应字节，不缓存 `/data` 和 `/refresh` 响应。

缓存文件按渲染参数区分：

- `sk`、`head`、`homo`：缓存 PNG。
- `sneak`、`dsk`、`dhead`：缓存 GIF。

`/face/{type}/{content}` 后续可复用同一套缓存机制，但优先级低于 3D 渲染接口。

## 缓存目录

默认目录：`render-cache/`

建议部署时挂载到持久化目录：

```text
/app/render-cache
```

目录结构：

```text
render-cache/
  {uuid}/
    {paramsMd5}.png
    {paramsMd5}.gif
```

缓存目录使用玩家 `uuid`。刷新皮肤是手动触发，被动失效也会先读取数据库中的玩家记录判断是否过期，因此以 `uuid` 作为缓存归属更直接：刷新指定玩家时可以删除该玩家全部渲染缓存，不需要再通过皮肤 hash 反查。

## 缓存元数据

缓存文件不写入数据库，数据库只保存缓存索引和参数元数据。这样可以避免数据库保存大二进制文件，同时支持：

- 按参数 MD5 精确命中缓存。
- 按总容量、条目数或最后访问时间清理缓存。
- 刷新皮肤时根据 `uuid` 查询并删除该玩家旧缓存文件。
- 后续排查缓存命中率和热点参数。

新增表建议命名为 `render_cache`：

```sql
CREATE TABLE IF NOT EXISTS render_cache
(
    `uuid`        CHAR(36)        NOT NULL COMMENT '玩家 uuid',
    `params_md5`  CHAR(32)        NOT NULL COMMENT '规范化参数 MD5',
    `ext`         VARCHAR(8)      NOT NULL COMMENT '文件后缀, 例如 png 或 gif',
    `skin_hash`   CHAR(64)        NOT NULL COMMENT 'Mojang 皮肤纹理 hash, 用于排查和比对',
    `size`        BIGINT UNSIGNED NOT NULL COMMENT '文件大小, 单位字节',
    `created_at`  BIGINT UNSIGNED NOT NULL COMMENT '创建时间戳',
    `last_access` BIGINT UNSIGNED NOT NULL COMMENT '最后访问时间戳',
    PRIMARY KEY (`uuid`, `params_md5`, `ext`),
    INDEX `idx_render_cache_uuid` (`uuid`),
    INDEX `idx_render_cache_skin_hash` (`skin_hash`),
    INDEX `idx_render_cache_last_access` (`last_access`),
    INDEX `idx_render_cache_size` (`size`)
) ENGINE InnoDB
  DEFAULT CHARSET UTF8MB4;
```

命中缓存时更新 `last_access`。写入缓存时先写文件，再插入或更新 `render_cache`；如果数据库写入失败，应删除刚写入的文件，避免孤儿文件持续增长。

## 参数摘要算法

缓存文件名使用规范化参数文本的 MD5，避免文件名过长。数据库不展开存储渲染参数，只保存 `params_md5` 和后缀名；读取时用同一套算法重新计算 MD5 即可定位缓存文件。

规范化参数文本必须稳定，字段顺序固定，字段值使用最终生效值，字段必须包含：

- 缓存版本：例如 `cacheVersion=1`，渲染算法或默认参数变化时递增。
- 渲染器标识：例如 `renderer=tavolo-cpu-v1`，用于区分渲染实现变更。
- `position`：`sneak`、`sk`、`dsk`、`head`、`dhead`、`homo`。
- `slim`：最终生效的模型类型。
- `bg`：最终 ARGB 背景色。
- `light`：最终 ARGB 光照参数，空值也要参与键。
- `head`：最终头部缩放。
- `x`、`y`、`duration`：仅 GIF 相关参数，按最终默认值入键。
- 输出尺寸、抗锯齿等级、是否使用 3D voxel overlay。

MD5 只用于本地缓存文件寻址，不用于安全校验；这里的目标是短文件名和稳定命中。

示例规范化文本：

```text
cacheVersion=1
renderer=tavolo-cpu-v1
position=dsk
slim=true
bg=ff1f1b1d
light=null
head=1.0
frameCount=20
pitch=20
duration=40
width=600
height=900
aa=1
voxelOverlay=true
```

示例文件路径：

```text
render-cache/22df77dd37b0414b8f1e3c7d2585fc79/4c2f7f2b4f70d5a8f7f8f8c7d7a9e123.gif
```

## 读写流程

1. 路由解析参数并拿到 `SkinData`。
2. 根据输出后缀和规范化参数计算 `paramsMd5`，`uuid` 只作为目录和数据库主键的一部分，不进入参数 MD5。
3. 查询 `render_cache`，如果 `(uuid, paramsMd5, ext)` 记录存在且缓存文件可读，更新 `last_access` 后直接返回文件字节。
4. 如果记录存在但文件丢失，删除这条 `render_cache` 记录并按未命中处理。
5. 未命中时调用 Tavolo 渲染器生成字节。
6. 先写入同目录临时文件，再原子移动为正式文件，避免并发请求读到半文件。
7. 写入 `render_cache` 元数据。
8. 触发总量控制，必要时删除最旧缓存。

临时文件命名：

```text
{paramsMd5}.{pid}.{threadId}.tmp
```

并发控制先采用文件原子写入即可。后续如果同一热 key 并发较高，再增加进程内 `ConcurrentHashMap<uuid:paramsMd5:ext, Mutex>` 避免重复渲染。

## 总量控制

缓存总量建议使用两个上限：

- 最大文件总大小：默认 `2 GiB`。
- 最大条目数：默认 `10000`。

两者任一超限都触发清理。清理顺序按 `last_access ASC` 删除最久未使用的记录和文件，直到低于水位线。

建议设置高低水位，避免每次写入都只删除一个文件：

- 高水位：`maxBytes` / `maxEntries`。
- 低水位：高水位的 `90%`。

写入新缓存后，如果超过高水位，则删除到低水位以下。

清理流程：

1. 查询当前 `SUM(size)` 和 `COUNT(*)`。
2. 如果超限，按 `last_access ASC` 分批查询候选记录。
3. 逐个删除文件。
4. 删除对应 `render_cache` 记录。
5. 文件不存在也视为删除成功，并清理数据库记录。

缓存配置建议放入 `config.yml`：

```yaml
renderCache:
  enabled: true
  dir: render-cache
  maxBytes: 2147483648
  maxEntries: 10000
  lowWatermarkRatio: 0.9
```

## 失效策略

刷新皮肤时，无论 Mojang 返回的新 `hash` 是否变化，都可以通过 `render_cache.uuid` 查询该玩家对应的缓存记录并删除文件：

```text
render-cache/{uuid}/
```

`refreshByName` 和 `refreshById` 都需要执行同一逻辑：

1. 刷新前读取旧 `SkinData`。
2. 获取新 `SkinData`。
3. 查询 `render_cache WHERE uuid = old.uuid`。
4. 删除查询到的缓存文件。
5. 删除对应 `render_cache` 记录。
6. 兜底删除 `render-cache/{old.uuid}` 空目录。
7. 删除旧皮肤原图缓存文件。
8. 写入新数据库记录。

如果希望减少无变化刷新导致的缓存抖动，也可以先比较 `old.hash` 与 `new.hash`：hash 未变化时保留缓存；hash 变化时按 `uuid` 清空缓存。默认建议直接按 `uuid` 清空，逻辑更简单，也符合手动刷新语义。

注意：当前皮肤原图文件名已经使用 `uuid.png`，渲染缓存也使用 `uuid` 分目录，便于刷新和排障。`skin_hash` 仍保留在元数据表中，用于确认缓存生成时对应的皮肤版本。

## Docker 配置

容器应新增渲染缓存挂载：

```yaml
volumes:
  - ./skin:/app/skin
  - ./render-cache:/app/render-cache
```

迁移到 Tavolo 后不再需要 `xvfb`、GTK、Prism 参数或 X server。启动命令保持：

```bash
java -jar app.jar
```

## 数据访问层替换建议

当前项目只需要少量 CRUD：玩家皮肤记录、渲染缓存记录、缓存统计和 LRU 清理。MyBatis 对这类场景偏重，实际实现已保留 HikariCP 连接池，并替换为小型 JDBC DAO。

当前落地结构：

- `Database`：读取现有 `db.properties`，初始化 Hikari，并创建 `skin`、`render_cache` 表。
- `SkinDao`：负责玩家皮肤记录的读取和写入。
- `RenderCacheDao`：负责缓存命中、写入、按 `uuid` 删除、按 `last_access` 查询 LRU 候选记录。

该方案没有新增 Exposed 依赖，依赖体积更小；当前查询也足够简单，可维护性可以接受。后续如果缓存统计和管理后台查询变复杂，再迁移到 Exposed SQL DSL。


## GIF 编码和量化优化判断

当前更高价值的优化点在渲染前置阶段：GIF 每帧复用同一个 `Scene` 和 mesh，避免重复生成 3D voxel overlay。GIF 编码/量化也有可优化空间，但应放在第二阶段：

- 当前 Tavolo GIF 编码会逐帧量化和抖动，CPU 成本不低。
- 可以考虑为同一 GIF 使用全局色表，减少每帧量化开销。
- 但全局色表可能降低旋转光照帧的颜色质量，需要图像对比后再启用。

因此第一阶段不改 GIF 编码器，只优化渲染资源复用和文件级结果缓存。
